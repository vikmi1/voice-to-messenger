# Voice-to-Messenger — бэкенд

Тонкий Flask-прокси: держит API-ключи, применяет системный промпт и стили,
управляется через веб-панель. Приложение шлёт сюда текст (или аудио) и получает
готовое сообщение.

## Запуск локально

```bash
cd backend
python -m venv venv
venv\Scripts\activate            # Windows;  source venv/bin/activate — Linux/mac
pip install -r requirements.txt
copy .env.example .env           # cp на Linux/mac; впиши ADMIN_PASS и SECRET_KEY
python app.py
```

Сервер поднимется на `http://localhost:8000`.

## Настройка

Открой `http://localhost:8000/admin` (логин/пароль из `.env`). Вкладки:

- **Провайдеры** — тип API, base_url, ключ и **обе модели**: для обработки текста и
  для распознавания речи. Выбор активного провайдера. В выпадашках — подобранные
  модели с классом цены и ценой (см. «Каталог моделей»), но поля остаются
  текстовыми: можно вписать что угодно руками. Кнопка «Список» у модели обработки
  дополнительно тянет живой перечень моделей у самого провайдера.
- **Распознавание** — только выбор провайдера, который распознаёт речь; его модель
  задаётся в карточке этого провайдера. В списке только OpenAI-совместимые
  провайдеры: у Anthropic нет API распознавания речи. Если сменить тип API у
  выбранного провайдера, ASR переключится на первого доступного.
- **Живой перевод** — три модели экрана живого перевода: потоковое распознавание,
  перевод и синтез речи (см. «Живой перевод»). Пустая модель озвучки оставит перевод
  бегущим текстом. Голос выбирается кнопками «пол → имя → настроение», список тянется
  живым запросом у провайдера. Здесь же — предел длины одной сессии.
- **Системный промпт** — базовое правило «вернуть только чистый текст».
- **Стили** — тоны (Мой стиль / Дружелюбно / Деловой). У «Моего стиля» промпт пустой:
  тон задают few-shot-примеры сообщений пользователя, которые приложение шлёт в поле
  `examples`. Старый набор из четырёх стилей заменяется на эти три автоматически при
  первом чтении конфига (признак старого набора — отсутствие стиля с id `mine`).
- **Языки** — цели перевода.
- **Тест** — прогон текста через сохранённые настройки; провайдер и модель можно
  переопределить, ничего не сохраняя, чтобы сравнить их между собой. Прогоны стоят
  денег и попадают в журнал расхода наравне с обычными запросами.
- **Расход** — сколько потрачено: отдельной карточкой за сегодня, дальше итоги за
  выбранный период, разбивка по моделям и дням, последние запросы (см. «Учёт расхода»).
  Сутки режутся по часовому поясу того, кто смотрит: панель передаёт свой сдвиг от UTC
  параметром `tz_offset`, иначе вечерняя диктовка попадала бы во вчерашний UTC-день.
- **Приложение** — API-токен приложения и админ-токен (панель на телефоне).

Изменения применяются без перезапуска (конфиг читается на каждый запрос).

Те же настройки правятся с телефона: Настройки → 7 нажатий по строке с версией
→ ввод админ-токена. См. `android/README.md`.

## Провайдеры

Поле **Тип API** определяет, как бэкенд разговаривает с провайдером:

| Тип | Кто подходит | Как устроено |
|-----|--------------|--------------|
| OpenAI-совместимый | OpenAI, Mistral, Groq, Ollama, LM Studio… | `POST {base_url}/chat/completions`, `Authorization: Bearer` |
| Anthropic (Claude) | Anthropic | `POST {base_url}/messages`, `x-api-key` + `anthropic-version`, `system` отдельным полем |

Простое правило: **Anthropic → тип Anthropic; всё остальное (OpenAI, Mistral,
локальные) → OpenAI-совместимый.**

Ключи можно не хранить в базе: если поле «API-ключ» пустое, бэкенд возьмёт
`<ПРОВАЙДЕР>_API_KEY` из окружения (например `ANTHROPIC_API_KEY`).

### `temperature` — параметр, который новые модели не берут

Для Anthropic он не отправляется вовсе: у Claude 5+ он устарел и вызывает
`400 temperature is deprecated for this model`. У OpenAI-совместимых по умолчанию
`temperature=0.3` — но не безусловно.

Модели OpenAI семейства gpt-5.6 (`luna`, `terra`, `sol`) принимают только значение
по умолчанию и отвечают `400 Unsupported value: 'temperature' does not support 0.3`.
То есть каталог предлагал три модели, каждая из которых гарантированно ломала
обработку сообщения — поймано аудитом 11.08.2026, до этого они просто не работали.

Заранее знать такие модели неоткуда: список растёт без нас, а в панели модель
вписывается руками. Поэтому `_post_chat` в `providers/openai_compatible.py` узнаёт
это из первого же отказа — повторяет запрос без параметра и запоминает пару
«адрес + модель» в `_NO_TEMPERATURE`, чтобы дальше не платить лишним заходом.
Память живёт до перезапуска процесса.

Правило на будущее: **это направление, а не особенность одной модели.** Если новая
модель отвечает 400 с упоминанием параметра — код разберётся сам, вмешиваться не надо.

Серверное распознавание речи работает только через OpenAI-совместимый
`/audio/transcriptions` — у Anthropic такого эндпоинта нет. Поэтому Anthropic
не показывается на вкладке «Распознавание», а `/api/transcribe` с таким
провайдером отвечает 400 с объяснением, а не 502.

Модель распознавания (`asr_model`) хранится **у каждого провайдера своя**, рядом с
моделью обработки текста. Раньше она была одна на весь конфиг, и переключение
ASR-провайдера оставляло чужую модель: `whisper-1` у Mistral не существует, как и
`voxtral` у OpenAI. Старый общий `asr.model` при первом чтении конфига переезжает
тому провайдеру, который его использовал, остальным проставляется рекомендуемая по
их `base_url`; блок `asr` схлопывается до `{"provider": "..."}`.

## Каталог моделей

`catalog.py` — короткий подобранный список моделей на провайдера: что имеет смысл
выбирать, к какому классу цены относится (`budget` / `balanced` / `premium`) и
сколько стоит. У провайдеров сотни моделей, но для переписывания коротких сообщений
осмысленны единицы.

Живёт на сервере, а не в панелях: обновление цен не требует пересборки APK, и обе
панели (веб и приложение) тянут его из `GET /admin/api/catalog`. Провайдер узнаётся
по `base_url`, а не по ключу в конфиге — ключ может быть любым («groq», «work»).
Незнакомый адрес просто останется без подсказок, поля моделей продолжат работать
как обычный текстовый ввод.

Цены в файле — из официальных прайсов, руками. Устареют — правится один список,
деплой бэкенда, приложение подхватит само.

У каждой модели цена записана дважды: `price` — строка для человека (в ней бывают
оговорки вроде «до такой-то даты»), `in` / `out` / `per_min` — числа для подсчёта
расхода. **Правишь цену — правь обе формы.**

### Модель существует ≠ модель годится для роли

Главное правило каталога: **что предлагаешь для роли, то и должно эту роль уметь.**
Пользователь выберет именно предложенное — и получит ошибку провайдера, которую не
может ни понять, ни исправить. Наличие имени в `GET /models` не обещает ничего:
эндпоинт перечисляет всё вперемешку.

Проверено запросами 11.08.2026:

| Модель | Где предлагалась | Что отвечает на самом деле |
|---|---|---|
| `voxtral-small-latest` | распознавание Mistral | `400 Invalid model` — она только в `/chat/completions` |
| `voxtral-mini-transcribe-realtime-2602` | распознавание Mistral | `400 only supports realtime transcription` |
| `gpt-realtime-translate` | распознавание OpenAI | `404 Invalid URL` — это WebSocket-модель, HTTP-эндпоинта нет |
| `voxtral-mini-tts-2603` без голоса | озвучка Mistral | `400 Either ref_audio or voice must be provided` |

Первая убрана из каталога совсем. Потоковые остались — они нужны живому переводу, —
но разведены по двум спискам: `realtime_asr_models()` для живого перевода и
`file_asr_models()` для обычного распознавания. Выпадашки берут каждая своё:
в вебе — `realtimeAsr()` и `fileAsr()`, в приложении — `realtimeAsrFor()` и
`fileAsrFor()`.

Отдельно от выпадашек **отказывает и сам `/api/transcribe`**: `catalog.is_realtime_only()`
ловит потоковую модель и отвечает 400 с подсказкой, какую поставить. Так починка
работает и там, куда новый список ещё не доехал, — панель на телефоне получает
каталог с сервера, но фильтрует его своим кодом, то есть до пересборки APK.

## Живой перевод

`live_translate.py` — мост между приложением и потоковым распознаванием. Приложение
открывает WebSocket на `/api/live` и льёт туда PCM 16 кГц с микрофона; мы держим второй
WebSocket — к `/v1/audio/transcriptions/realtime` провайдера, — режем распознанный текст
на фразы и переводим каждую отдельной моделью, а при включённой озвучке ещё и синтезируем
её в mp3.

**Режима два, и выбирает его модель распознавания** (`catalog.realtime_mode`):

| | три модели (`transcribe`) | одна модель (`translate`) |
|---|---|---|
| кто | Voxtral Realtime + LLM + Voxtral TTS | `gpt-realtime-translate` |
| класс | `Bridge` | `SoloBridge` |
| расход | `live_stt` + `live_translate` + `live_tts` | одна строка `live_speech` |
| счёт | секунды речи, токены, символы | минуты выходного аудио |
| язык говорящего | определяет модель | определяет модель |
| оригинал в ленте | есть | нет (см. ниже) |

Voxtral Realtime только распознаёт, поэтому перевод и синтез — отдельные вызовы.
Модель OpenAI делает всё сама; настройки «Перевод» и «Озвучка» при ней не читаются.

### Протокол одной модели (OpenAI)

Снят с живого эндпоинта 07.08.2026 — в документации он описан не целиком:

- адрес `/realtime/translations?model=gpt-realtime-translate`;
- язык перевода задаётся `session.update` — **обязательно**: по умолчанию модель
  переводит на испанский, и отвергнутый `session.update` связь не рвёт, а молча
  оставляет испанский. Поэтому мост ждёт `session.updated`, а не шлёт и забывает;
- звук уходит событием `session.input_audio_buffer.append` **в 24 кГц**; приложение
  пишет 16 — пересчитываем на сервере (`audioop.ratecv`), чтобы не трогать запись
  на телефоне и не гнать в полтора раза больше байт по мобильной сети;
- обратно идут два потока: `session.output_transcript.delta` (текст перевода) и
  `session.output_audio.delta` (PCM 24 кГц кусками по 0.4 с);
- завершение — `session.close`, ответ `session.closed`.

**Модель ведёт свою временну́ю шкалу.** Пока человек говорит, аудио идёт вровень с речью;
пока молчит — не идёт вовсе, но шкала копится и по `session.close` вываливается целиком.
В замере это 29 секунд ровных нулей на 3 секунды речи. Поэтому мост, во-первых, не
пересылает в приложение куски с нулевым пиком, во-вторых, вешает трубку, как только
после «стоп» пошла сплошная тишина: хвост последней фразы приезжает раньше неё.

**Фраза закрывается паузой в 5 секунд, а не в 1.8.** Эта модель отдаёт перевод вместе
со своей озвучкой — с отставанием и провалами в пару секунд посреди фразы. На коротком
пороге лента резалась на обрывки («Это» | «вторая фраза: вы всё ещё меня слышите?»).

**Оригинала в ленте нет.** Исходный текст модель отдаёт только с включённой расшифровкой
входа (`audio.input.transcription.model`) — это отдельная платная модель поверх
($0.017 / мин против $0.034 за сам перевод). Платить в полтора раза больше за подпись
под переводом незачем; если понадобится — включается одним полем в `_session_config`.

**Почему протокол зашит руками, а не взят из SDK.** Официальный `mistralai[realtime]`
тянет в образ pydantic, httpx и весь клиент ради полутора десятков строк JSON.
Формат сообщений снят с `mistralai.extra.realtime` и продублирован в модуле:
клиент шлёт `session.update` / `input_audio.append` / `input_audio.flush` /
`input_audio.end`, сервер отвечает `session.created`, `transcription.language`,
`transcription.text.delta`, `transcription.segment`, `transcription.done`, `error`.

**Где кончается фраза.** Потоковая модель не обещает знаков препинания, поэтому границу
ищем тремя способами сразу: конец предложения, накопившаяся длина (220 символов) и пауза
в речи (1.8 с молчания модели плюс 0.8 с без звука — см. про хвост ниже). Событие
`transcription.segment` обрабатывается только как сигнал границы, текст всегда берётся из
дельт, иначе одно и то же попало бы в перевод дважды; на практике Voxtral Realtime его
не присылает вовсе — проверено прямым подключением, приходят только
`transcription.text.delta`.

**Форма ответа синтеза различается у провайдеров — и это грабли.** Mistral отдаёт
`POST /audio/speech` как JSON `{"audio_data": "<base64 mp3>"}`, OpenAI — сами байты
файла. Отличаем по `Content-Type`. Первая версия возвращала тело ответа как есть, и
приложение скармливало плееру JSON-документ: перевод работал, деньги тратились, звука
не было вовсе. Форма была взята из модели официального SDK — **проверяй реальный
эндпоинт, а не описание клиента.** Поле голоса на проводе называется `voice`
(не `voice_id`), и у Mistral оно обязательно: без него приходит 400
«Either ref_audio or voice must be provided».

**Голоса** (`voices.py`, `GET /admin/api/voices`) тянутся живым запросом у провайдера.
У Mistral список свой, с полом, языками и тегами; настроение там — часть голоса
(«Paul - Happy» и «Paul - Sad» это два разных голоса), поэтому «пол → имя → настроение»
ложится на список один в один. У OpenAI эндпоинта списка нет вовсе (404), набор зашит
в модуле и проверен обращением к боевому API; настроение задаётся отдельным полем
`instructions` — оно и стоит за кнопками готовых настроений. **Пол у OpenAI не
показывается:** официально они его не публикуют, а угадывать по именам — выдавать
догадку за факт.

**Где кончается фраза — важное про хвост.** Замеры на боевом API: во время речи паузы
между дельтами не больше 0.64 с, а вот **после конца звука модель придерживает
дослышанные слова ещё ~3.3 с**. Таймер молчания, сработавший внутри этого окна, резал
фразу пополам, и хвост приезжал отдельной репликой — лишний вызов перевода и рваная
речь в наушнике. Поэтому, как только приложение перестаёт слать звук (0.8 с тишины),
мы досылаем `input_audio.flush`: модель отдаёт хвост сразу, кусок закрывается целым,
а задержка последней фразы падает на те же три секунды.

### Где в режиме трёх моделей уходили секунды

Замер 07.08.2026: синтезированная немецкая фраза из четырёх предложений (6.6–6.9 с)
льётся в настоящий `/api/live` порциями по 100 мс, как с телефона; отсчёт от конца
звука, по три прогона на конфигурацию, в таблице медианы.

| | было | стало |
|---|---|---|
| последний перевод в ленте | **+2.10 с** (1.80…2.53) | **+0.80 с** (0.62…1.14) |
| последняя озвучка в наушнике | **+3.17 с** (3.03…3.86) | **+2.26 с** (1.87…3.21) |
| простой куска в очереди | 1.05 с | 0.57 с |

Причина была одна: `_translate_worker` переводил и **тут же сам синтезировал**, а
следующий кусок ждал в очереди, пока приедет mp3 предыдущего. В журнале это видно
прямо: кусок закрыт на +0.99 с, а перевод начался на +1.66. Синтез вынесен в
`_speech_worker` со своей очередью и идёт следующей фразе внахлёст.

По тексту выигрыш надёжный — диапазоны «было» и «стало» не пересекаются вовсе.
По звуку он есть, но шумный: TTS отвечает от 0.9 до 1.6 с от прогона к прогону,
и диапазоны налегают друг на друга. Порядок озвучки проверялся в каждом прогоне
и не нарушился ни разу — очередь синтеза сохраняет его сама.

**Что осталось непочатым.** Синтез — по-прежнему полный круг: ждём файл целиком,
потом отдаём. Стриминг `/audio/speech` сдвинул бы начало звука на сотни миллисекунд,
но требует правок в приложении: плеер сейчас ждёт готовый mp3 на фразу.

### Язык говорящего задать нельзя — ни одной из двух моделей

Проверено прямым подключением 07.08.2026. У **Voxtral Realtime** вся сессия — четыре поля:

```json
{"request_id": "…", "model": "…", "audio_format": {…}, "target_streaming_delay_ms": null}
```

`session.update` с `language` отвергается (`Extra inputs are not permitted`), в адресе
`?language=de` проглатывается молча и никуда не попадает. У **gpt-realtime-translate**
во входе только `noise_reduction` и `transcription`; язык есть лишь на выходе
(`audio.output.language`, по умолчанию `es`).

Поэтому `source_lang` в протоколе с приложением до распознавания **не доходит** и
меняет только наше поведение: отключает ветку «языки совпали — переводить нечего»
и добавляет две строки в промпт перевода.

**Чего это НЕ чинит.** Если распознавание ошиблось языком, оно пишет речь чужим
алфавитом: немецкое «Würden Sie bitte mit mir langsam reden» приехало как «Вердан с
битами, мир лангзам рейден». Из текста это восстанавливается не всегда — замер на
боевом ключе:

| фраза | small | medium | large |
|---|---|---|---|
| «Хало, их мёхте айн кафе одер айн тее» | ✔ «я бы хотел кофе или чай» | — | — |
| «Вердан с битами, мир лангзам рейден» | ✘ вернул как есть | ✘ «мир медленно едет» | ✘ «давайте медленно поедем вперёд с битами» |

Модель побольше не помогает. Видимую часть бага (расшифровка показана как готовый
перевод) `source_lang` убирает, саму ошибку распознавания — нет.

**Зацепка к скорости:** `target_streaming_delay_ms` Voxtral принимает (`0`, `200`,
`500` → `session.updated`), а мы его не задаём и работаем на умолчании. Не изучено.

### Прямое соединение приложения с OpenAI пока невозможно

Тоже 07.08.2026. Эфемерные ключи (`POST /v1/realtime/client_secrets`) выдаются и
пускают на `/realtime/translations`, но сессия там получается **не переводческая**:

```
ek_ + session.update → "Missing required parameter: 'session.type'."
минт {"type": "translation"} → "Supported values are: 'realtime' and 'transcription'."
минт {… "audio": {"output": {"language": "ru"}}} → "Unknown parameter"
```

С настоящим ключом тот же адрес отдаёт `"type": "translation"` и принимает язык.
То есть выдача эфемерных токенов про режим перевода ещё не знает, и прямое
соединение потребовало бы настоящего ключа в APK. Проверять заново, когда OpenAI
добавит `translation` в `session.type`.

Задержка при этом не аргумент: Hetzner → api.openai.com даёт **19 мс** в среднем
(13.7–40.6). Секунды в режиме трёх моделей заложены нами — таймеры 0.8 с и 1.8 с
плюс последовательные вызовы перевода и синтеза, — а не сетью.

### «Control frames must be final.» — в сокет писали два потока

Установлено 07.08.2026, воспроизведено локально. Симптом: в режиме одной модели
приложение показывает `Control frames must be final.` и вешает микрофон. Текст —
не наш и не OpenAI: так okhttp сообщает, что прочитал из сокета кадр с чужими
байтами. Ломается связка «наш сервер → телефон», модель тут ни при чём.

В сокет приложения пишем не мы одни. У simple_websocket есть фоновый поток: он
отвечает понгами на пинги okhttp (раз в 20 с) и раз в 25 с шлёт свои
(`SOCK_SERVER_OPTIONS`). Библиотека писателей не разводит. Пока кадры были мелкие,
каждый укладывался в буфер сокета целиком и с первого раза, и это сходило с рук.
Режим одной модели шлёт 25 КБ озвучки каждые 0.4 с — буфер переполняется, `send`
засыпает посреди кадра, Linux на время ожидания отпускает замок сокета, и фоновый
поток дописывает туда же свой пинг. Прямо в середину нашего кадра.

Замер на воспроизведении: наш поток сидел внутри `send(32010 B)`, когда
`simple_websocket.Base._thread` вошёл в `send` со своими 2 байтами пинга. С
`_OneWriterSocket` (замок на запись плюс `sendall` вместо `send`, который вправе
записать часть и молча потерять хвост) пинги уходят те же, а накладок ноль.

**На Windows не воспроизводится** — Winsock сам сериализует одновременные `send`.
Проверять такое надо на Linux, как в проде.

### Грабли протокола: что на самом деле значат 1011, 403 и 503

Установлено 06.08.2026 воспроизведением на боевом ключе — пробы гонялись прямо на сервере
(`ssh hetzner "docker exec -i voiceapp python -" < проба.py`), это самый короткий способ
поговорить с провайдером его же ключом.

**`1011 Upstream connection error` — симптом, а не причина.** Шлюз Mistral рвёт связь через
пару секунд после того, как сессия получила свою настоящую ошибку. Настоящая приезжает
раньше отдельным событием `{"type":"error","error":{"message":…,"code":…}}` — её и надо
искать, а не гадать по 1011. Чтобы она доходила до человека, при таком событии сессия
теперь останавливается сразу: раньше мы продолжали лить звук в мёртвый сокет, и текст
ошибки затирался тем самым 1011.

**`flush` до первой порции звука → `code 3051`** «Cannot flush audio before sending any
audio bytes», следом 1011. Ловилось на каждой сессии: между «сессия готова» и первым
словом человека проходит больше 0.8 с, и таймер хвоста срабатывал на пустом буфере.
Признак «хвост уже запрошен» поэтому взведён на старте и живёт полем объекта — завершению
сессии он нужен так же, как циклу приёма звука (иначе второй `flush` по пустому буферу
выдавал ту же ошибку сразу после «стоп»).

**`transcription.done` — конец куска, а не сессии.** Модель отвечает им на каждый `flush`,
то есть после каждой замолчавшей фразы, и продолжает распознавать дальше. Пока код считал
это событие концом распознавания, переводилась ровно одна фраза: чтение событий
прекращалось, звук лился в пустоту. Расходимся только по собственному `input_audio.end`.

**Неверная модель в URL → HTTP 403** на рукопожатии (не 1011). **OpenAI на этом пути →
HTTP 503**: эндпоинта `/audio/transcriptions/realtime` у них нет вовсе, потоковое
распознавание живёт по другому адресу и говорит на другом протоколе. Поэтому `resolve()`
отказывает провайдеру, у которого в каталоге нет realtime-модели, — с внятным текстом
вместо «HTTP 503». Незнакомый адрес (свой vLLM) пропускается: запрещать ему нельзя.

**Известная недоделка:** если ничего не говорить ~40 с, распознавание закрывает сессию
с `code 3804` «Timeout waiting for response from streaming transcription» — служебная
тишина раз в 10 с его не удерживает. На разговоре не проявляется.

**Что удерживает расход:**

- тишина в модель не отправляется — ворота по громкости стоят на устройстве
  (`SpeechGate.kt`, покрыт юнит-тестами); раз в 10 секунд уходит 0.1 с тишины,
  чтобы распознавание не сочло сессию брошенной;
- если язык говорящего совпал с языком перевода, перевод не вызывается вовсе;
- сессия закрывается сама по `live.session_limit_minutes` (по умолчанию 10).

Расход пишется **тремя строками на сессию**, а не на каждую фразу: один разговор — это
десятки кусков, и построчный журнал превратил бы вкладку «Расход» в ленту ни о чём.
Операции: `live_stt` (секунды аудио), `live_translate` (токены), `live_tts` (символы,
колонка `chars`).

Соединение занимает поток воркера на всю сессию — их всего восемь (2 воркера × 4 потока),
так что предел длины сессии не только про деньги.

## Учёт расхода

`usage_store.py` пишет строку на каждый запрос к провайдеру: обработку текста,
распознавание и прогон с вкладки «Тест». Пока это только наблюдение — ничего не
тарифицируется и не ограничивается, но по накопленным данным будет видно реальную
стоимость использования вместо оценок.

**Отдельный файл БД** (`usage.sqlite3` рядом с `config.sqlite3`), а не таблица в
конфиге: конфиг читается на КАЖДЫЙ запрос, и запись в тот же файл держала бы
блокировку. Путь переопределяется переменной `USAGE_DB_PATH`.

**В базе только сырые токены, деньги не хранятся.** Цена привязана к модели на момент
запроса и меняется; записанные доллары сделали бы историю несопоставимой при первой
же правке прайса. Стоимость считается на чтении, по текущему каталогу — поэтому
добавление модели в каталог пересчитывает и уже накопленную историю.

Модель, которой нет в каталоге, даёт стоимость `null` и показывается **прочерком**,
а не нулём: в отчёте про деньги «неизвестно» не должно выглядеть как «бесплатно».
В группировках для этого считается `unpriced`.

Расход снимается с провайдеров, а не оценивается:

- **OpenAI-совместимые** — при `stream=true` расход не приходит без
  `stream_options.include_usage`. Параметр фирменный для OpenAI, поэтому шлётся
  только на `api.openai.com`; у остальных `usage` разбирается из финального чанка,
  если провайдер его прислал сам (Mistral присылает).
- **Anthropic** — двумя событиями: вход в `message_start`, выход накопительным
  итогом в последнем `message_delta`. Оттуда же берутся `cache_read_input_tokens`
  и `cache_creation_input_tokens`.
- **Распознавание** — `/audio/transcriptions` с `response_format=json` длительность
  не сообщает (проверено: voxtral не сообщает). Длительность берётся по убыванию
  доверия, источник записывается в `audio_seconds_source`:
  1. `provider` — если прислал её в `usage` или `duration`;
  2. `container` — точная длительность из заголовка файла (`audio_meta.py`
     разбирает MP4/M4A и WAV без сторонних библиотек);
  3. `estimate` — последний рубеж для незнакомого формата: размер, делённый на
     4000 байт/с (приложение пишет 32 кбит/с моно).

  **Оценка верна только для аудио приложения:** тот же звук в 64 кбит/с она растянет
  с 24.5 с до 40 с, а трёхсекундный WAV сочтёт за 24 с — из-за этого и появился разбор
  заголовка. Рядом всегда хранится `audio_bytes`, по нему можно пересчитать.

**Кредит** — единица показа, `catalog.CREDIT_USD` (сейчас $0.001), округление вверх:
ненулевой расход никогда не показывается нулём. Сообщение на бюджетной связке стоит
единицы кредитов, на флагманской модели — полтора-два десятка.

Строк накапливается мало по природе продукта (сотни в месяц), поэтому ротации нет.

### Когда спрашивать стоимость: гонка, которая съедала половину показов

`/api/process` отдаёт `X-Usage-Id` **заголовком**, то есть до первого куска текста, —
а строку в журнал пишет `finally` генератора, то есть после последнего. Между этими
моментами id уже известен, но спрашивать по нему нечего.

Приложение спрашивало сразу по заголовку и получало 404. Хуже, что это был конец:
id к тому моменту помечен посчитанным, второй попытки нет — расход молча терялся.
В логах 09–10.08.2026 четыре таких 404 из шести запросов.

Починено с двух сторон, и вторая нужна не меньше первой:

- в приложении стоимость спрашивается в `finally`, когда поток закончился, — при
  любом исходе, включая отмену на середине (токены к тому моменту уже потрачены);
- `/api/usage/<id>` ждёт появления строки до трёх секунд вместо мгновенного 404.

Одной правки в приложении мало: строка пишется *после* последнего куска, поэтому
гонка осталась бы и при запросе «в конце» — просто окно стало бы уже. Ожидание на
сервере закрывает её целиком и заодно чинит уже установленные сборки.

Проверяется воспроизведением самой гонки: запросить стоимость, не дочитав поток.
Должно прийти 200 после короткого ожидания, а не 404.

«Админ» — заголовок `X-Admin-Token` с админ-токеном из панели; им пользуется
приложение. Обычный `api_token` в админку не пускает.

`/api/process` отдаёт id строки расхода **заголовком** `X-Usage-Id`: тело ответа —
поток текста, метаданные в него не вложить, а заголовки уходят до тела. По этому id
приложение потом спрашивает `/api/usage/<id>` и показывает потраченные кредиты —
**когда поток дочитан**, а не по приходу заголовка; почему это важно, см. «Когда
спрашивать стоимость».
`/api/transcribe` возвращает свой id полем `usage_id` в JSON. У `/api/live` id нет:
расход сессии приходит прямо в сокет сообщениями `{"type":"credits","spent":N}`.

### Протокол `/api/live`

Токен идёт заголовком `Authorization: Bearer` при рукопожатии; отказ приходит
сообщением `{"type":"error","message":"unauthorized"}`, а не HTTP-кодом — у WebSocket
ответа с кодом уже нет.

| Направление | Сообщение | Смысл |
|-------------|-----------|-------|
| приложение → сервер | `{"type":"start","target_lang":"ru","speak":true}` | обязательный первый кадр |
| приложение → сервер | двоичный кадр | PCM_S16LE, 16 кГц, моно |
| приложение → сервер | `{"type":"config","target_lang":"de","speak":false}` | смена языка/озвучки на ходу |
| приложение → сервер | `{"type":"stop"}` | штатное завершение |
| сервер → приложение | `{"type":"ready","limit_seconds":600}` | распознавание поднялось |
| сервер → приложение | `{"type":"language","code":"en"}` | язык говорящего, определён моделью |
| сервер → приложение | `{"type":"partial","text":"…"}` | накопленная незакрытая фраза целиком |
| сервер → приложение | `{"type":"unit","id":1,"original":"…"}` | фраза закрыта, ушла на перевод |
| сервер → приложение | `{"type":"translation","id":1,"text":"…"}` | перевод фразы |
| сервер → приложение | `{"type":"audio","id":1,"format":"mp3","data":"<base64>"}` | озвучка фразы |
| сервер → приложение | `{"type":"credits","spent":42}` | накопленный расход сессии |
| сервер → приложение | `{"type":"limit"}` | время сессии вышло |
| сервер → приложение | `{"type":"error","message":"…"}` | ошибка (не всегда фатальная) |
| сервер → приложение | `{"type":"done"}` | сессия закрыта, расход записан |

`partial` присылается целиком, а не дельтой: приложению нечего склеивать, и потерянное
по дороге сообщение чинит само себя.
